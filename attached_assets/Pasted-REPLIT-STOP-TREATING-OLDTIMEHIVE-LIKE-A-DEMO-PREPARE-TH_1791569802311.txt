PHASE 1: FULL APPLICATION AUDIT

Inspect the entire repository, including:

* Frontend and navigation.
* Authentication and account management.
* Backend APIs and database connections.
* User profiles and account settings.
* Following, followers, and friend relationships.
* Feed, For You, Following, and content discovery.

* Direct messaging and notifications.
* Communities, groups, and other social features.
* Creator accounts, verification badges, and monetization.
* Administrative and moderation functionality.
* Mobile responsiveness and accessibility.
* Security, performance, error handling, and deployment.

For every feature, determine whether it is:

1. Fully implemented and working.
2. Implemented but not connected to a real backend.
3. Partially implemented.
4. Simulated or using mock data.
5. Broken.
6. Missing.

Do not mark a feature production-ready simply because its screen renders or a button responds to a click.

PHASE 2: REAL AUTHENTICATION AND USER ACCOUNTS

Prepare the application for real users using our intended AWS-first architecture.

* Configure AWS Cognito as the primary authentication provider if it is not already connected.
* Implement real registration, login, logout, session persistence, email verification where appropriate, and password recovery.
* Ensure users can access only their own private account information.
* Enforce authorization on the backend.
* Ensure protected pages and APIs reject unauthorized requests.
* Handle expired sessions, invalid credentials, duplicate registrations, network failures, and account deletion correctly.
* Never expose private credentials or privileged API keys in frontend code.
* Do not introduce unnecessary Apple or Google login integrations just because you assume they are required for store approval.

Inspect the current authentication implementation before modifying it. Do not replace a working system without explaining why.

PHASE 3: DATABASE AND REAL DATA

Real users must be able to interact with each other.

* Connect every required feature to the actual production database and backend.
* Remove mock data from production flows.
* Persist account changes, posts, comments, reactions, follows, relationships, and other supported features.
* Ensure data belongs to the correct user and is not accidentally shared with unauthorized users.
* Add appropriate database constraints, indexes, validation, and migrations.
* Handle duplicate requests and concurrent updates safely.
* Provide loading, empty, success, and error states.
* Ensure refreshing the page or signing in again does not unexpectedly erase persistent user data.

Do not assume a database is configured simply because its environment variables exist.

Inspect the existing AWS setup before selecting or provisioning additional services. Do not create duplicate databases or infrastructure unnecessarily.

PHASE 4: SOCIAL FEATURES MUST ACTUALLY WORK

Test the entire user journey between multiple independent accounts.

For example:

* User A creates an account.
* User A completes a profile.
* User B creates a separate account.
* User A follows User B.
* User B publishes a post.
* User A can discover and interact with that post according to the applicable visibility settings.
* Likes, comments, saves, and follow relationships persist correctly.
* Private accounts and restricted content remain private.
* Blocking and reporting work correctly.
* Notifications correspond to real events rather than fabricated activity.

Apply the same standard to messaging, stories, communities, groups, media uploads, and other implemented features.

If a feature requires an external service that is not configured, identify the missing dependency and implement the appropriate integration only when it can be completed safely. Do not fake successful functionality.

Inspect and test:

* Media previews.

PHASE 6: SECURITY AND PRIVACY

Perform a serious production security review.

Check:

* Authentication and authorization.
* Broken access controls.
* Cross-account data leakage.
* Input validation and output encoding.
* Cross-site scripting and injection risks.
* Cross-site request forgery where applicable.
* Rate limiting and abuse prevention.
* Secure session and cookie configuration.
* File-upload security.
* API permissions.
* Database access policies.
* Secret management.
* Error messages that expose sensitive information.
* Dependency vulnerabilities.
* Administrative access controls.

Ensure public, private, and restricted content follows the intended access rules.

Never trust a user ID, account type, verification status, subscription status, or payment amount supplied by the client without validating it on the server.

Do not expose sensitive stack traces or internal infrastructure details to users.

PHASE 8: MONETIZATION READINESS

Our business model includes paid verification, subscriptions, creator features, digital purchases, and potentially creator payouts.

Prepare the architecture so these can be implemented securely.

* Verify paid entitlements on the backend.
* Never grant a paid badge because a frontend variable says the user paid.
* Protect subscription and transaction records.
* Prevent duplicate processing of payment events.
* Handle refunds, cancellations, and expired subscriptions.
* Keep creator earnings and transaction records consistent.
* Verify the applicable Apple and Google billing rules before implementing purchases inside their mobile apps.
* Do not assume Stripe is required for every payment flow.
* Do not assume Apple or Google will handle all creator payouts.
* Do not activate real charges or payouts without the required configuration and safeguards.

If payment infrastructure is not ready, prepare the integration points without pretending transactions are operational.

* Prevent duplicate submissions.
* Handle timeouts and temporary service failures.
* Prevent accidental loss of unsaved edits.
