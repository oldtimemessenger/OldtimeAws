Both platforms give creators a central place to understand how their accounts and content perform.

For example, TikTok Studio provides account statistics, individual video performance, follower analytics, and monetization information. Instagram’s professional tools similarly provide content insights and account performance data.  

Here’s how I’d translate that into Oldtimehive.

Imagine a creator opens Oldtimehive, visits their profile, and taps Creator Dashboard.

The creator can tap any statistic to see its history and understand whether their account is growing.

3. Profile visitors: See who’s checking you out 👀

BRO, THIS ONE IS IMPORTANT.

I would give Oldtimehive two separate features.

Feature 1: Profile visit analytics

Every creator can see how many times their profile was visited.

For example:

Profile activity

* 2,450 profile visits this week.
* 680 visits came from your videos.
* 320 visits came from your Blasts.
* 190 visits came from search.
* Other visits came from different sources.

This helps creators understand what brings people to their profiles.

Feature 2: Who viewed your profile

You could also introduce an optional Profile Visitors feature.

It would show a list of people who viewed a creator’s profile, provided the feature’s privacy rules allow it.

For example:

Visitor	Activity
@alex	Visited your profile
@maria	Visited your profile
@jordan	Visited your profile

But there’s an important distinction.

Counting profile visits and identifying individual visitors are two different things.

I’d make identifiable profile viewing optional and transparent. Users should know when their identity may be shown to other people, with appropriate privacy controls.

Creators should still receive aggregate visit counts when individual visitor identities aren’t available.

That gives Oldtimehive useful analytics without forcing everybody to reveal their browsing activity.

Imagine a creator uploads a 30-second video.

The graph might show:

* 100% of viewers started watching.
* 72% remained at 5 seconds.
* 48% remained at 15 seconds.
* 21% reached the end.

Those figures would help the creator understand where viewers lose interest.

My favorite addition: Content discovery sources

Tell creators where their views came from.

For example:

* For You feed
* Following feed
* Profile
* Search
* Shared links
* Blasts
* Communities

Now creators can understand whether Oldtimehive is recommending their content or whether their followers are driving the views.

Only display sources that Oldtimehive can actually measure.

8. Here’s the exact prompt to give your developer

I’m writing this for your current mobile-first Oldtimehive website, so the dashboard can become part of your existing product rather than a disconnected page.

The goal is to build the real feature, not just a visual mockup.

Build a complete, production-minded Creator Studio and Analytics Dashboard for Oldtimehive, inspired by the best functionality of TikTok Studio and Instagram Professional Dashboard, while creating a distinct Oldtimehive experience.

IMPORTANT PROJECT REQUIREMENTS

* Work within the existing Oldtimehive codebase.
* Preserve existing navigation, authentication, profiles, posts, videos, Blasts, communities, messaging, and monetization features.
* This project is currently a mobile-first web application.
* Do not migrate the application to a native framework as part of this task.
* Do not require Replit-specific infrastructure or add Replit branding.
* Keep the implementation compatible with a future migration to a separate hosting environment and a future mobile application.
* Inspect the existing architecture and data models before making changes.
* Reuse existing components, styles, APIs, and data wherever possible.
* Do not replace working functionality with mockups or hardcoded sample data.

1. CREATOR STUDIO ENTRY POINT

Add a Creator Studio entry point accessible from the user’s profile and account menu.

The interface should feel like a premium creator analytics product, not an administrative dashboard.

Design requirements:

* Mobile-first responsive layout.
* Clean typography and carefully structured information hierarchy.
* Professional analytics cards.
* Interactive charts.
* Smooth but restrained transitions.
* Clear loading, empty, error, and success states.
* Accessible buttons, labels, and controls.
* Consistent styling with Oldtimehive’s existing design system.
* Dark and light theme compatibility if supported by the existing application.

On mobile, use a compact navigation system with Overview, Content, Audience, Growth, and Earnings tabs.

On larger screens, a sidebar navigation is acceptable.

2. OVERVIEW DASHBOARD

Build an overview screen containing:

* Total content views.
* Profile visits.
* Unique viewers, when reliably measurable.
* New followers.
* Net follower growth.
* Engagement rate.
* Total likes, comments, shares, and saves.
* A time-series chart of account performance.
* A recent content performance list.
* A summary of creator earnings, when applicable.
* Actionable insights based on real performance data.

Provide date filters for:

* Last 7 days.
* Last 28 days.
* Last 90 days.
* Custom date range.

Show comparisons with the previous equivalent period when sufficient data exists.

For each metric, clearly define what is counted, how it is calculated, and what time range applies.

3. PROFILE VISIT ANALYTICS

Implement profile visit tracking.

Record measurable profile visits using an appropriate server-side or event-processing architecture.

Capture only the minimum information needed to calculate analytics.

Where supported, attribute profile visits to measurable discovery sources, including:

* For You feed.
* Following feed.
* Search.
* Content pages.
* Blasts.
* Communities.
* Shared links.
* Direct profile navigation.
* Other measurable sources.

Avoid double-counting accidental repeated requests or automated traffic where practical.

Distinguish total visits from unique visitors.

Create a separate optional Profile Visitors feature if it can be implemented consistently with Oldtimehive’s privacy model.

This feature must have clear privacy controls, transparent behavior, and appropriate consent or disclosure.

Do not expose a visitor’s identity when their privacy settings or the product’s privacy rules prohibit it.

Aggregate profile visit counts must remain available even when individual identities cannot be shown.

4. INDIVIDUAL CONTENT ANALYTICS

Add a View Insights action to eligible content owned by the current user.

Support existing content types where practical, including videos, photos, Blasts, and stories.

For each content item, display applicable metrics:

* Total views.
* Unique viewers.
* Watch time.
* Average watch time.
* Video completion rate.
* Likes.
* Comments.
* Shares.
* Saves.
* Profile visits attributed to the content.
* Follows attributed to the content.
* Traffic sources.
* Performance over time.

For video content, provide a retention chart when sufficient playback event data exists.

Do not invent retention measurements or infer precise viewing behavior from simple page impressions.

Use consistent, documented definitions for views, impressions, unique viewers, and completed views.

Provide sorting and filtering by publication date, content type, views, engagement, and other supported metrics.

5. AUDIENCE ANALYTICS

Create an Audience tab with:

* Follower growth over time.
* New followers.
* Unfollows, where measurable.
* Net follower growth.
* Follower activity by day and hour.
* Broad geographic or language breakdowns when reliable data exists.
* Additional aggregated demographics only when collected appropriately and legally.

Protect audience privacy.

Suppress small demographic groups where needed to prevent identification.

Do not fabricate ages, locations, genders, or audience activity.

If a metric is unavailable, explain why and show a useful empty state.

6. GROWTH INTELLIGENCE

Create a Growth section that identifies meaningful patterns from real account and content data.

Examples include:

* Content receiving above-average views.
* Posts generating profile visits.
* Content converting viewers into followers.
* Changes in engagement over time.
* Times when followers are most active.
* Content formats performing best for a particular creator.

Each insight must be supported by actual data.

Explain the reason for each recommendation and distinguish measured facts from estimates.

Do not display fake AI insights or generate claims when the available sample size is insufficient.

Structure this feature so a future AI analysis service can be added without rebuilding the dashboard.

7. CREATOR EARNINGS

Create an Earnings tab integrated with existing monetization functionality.

Where the corresponding systems exist, display:

* Subscription revenue.
* Active subscribers.
* Subscription cancellations.
* Gifts received.
* Live-room revenue.
* Other supported creator revenue.
* Gross earnings.
* Platform fees.
* Refunds and adjustments.
* Estimated net earnings.
* Available payout balance, if a payout system exists.
* Payment history.
* Transaction status.

Keep the following financial concepts separate:

* Gross revenue.
* Platform commission.
* Taxes.
* Refunds and chargebacks.
* Pending earnings.
* Available payout funds.
* Completed payouts.

Do not invent payout balances or assume that all monetization transactions follow the same commission structure.

Do not implement unsupported payout functionality or claim that a creator has been paid without a verified payment record.

Include creator verification subscription status as a separate feature rather than incorrectly counting verification fees as creator earnings.

8. ANALYTICS EVENT ARCHITECTURE

Inspect the existing application and identify the correct locations for analytics events.

Implement reusable event tracking for supported actions such as:

* Content impression.
* Video playback start.
* Qualified video view.
* Playback progress.
* Video completion.
* Like.
* Comment.
* Share.
* Save.
* Profile visit.
* Follow.
* Unfollow.
* Subscription purchase confirmation.
* Gift transaction confirmation.
* Live-room engagement where measurable.

Use server-verified financial events for monetary records.

Prevent obvious duplicate events and repeated client submissions from inflating analytics.

Do not send sensitive message content, private chat data, passwords, authentication tokens, or unnecessary personal information to analytics systems.

Respect account deletion, privacy preferences, access controls, and applicable data-retention requirements.

Use batching or background processing where appropriate so tracking does not noticeably slow down the application.

9. DATA STORAGE AND SECURITY

Inspect the current application data architecture before implementing analytics persistence.

If the current backend already supports reliable analytics storage, reuse it.

Otherwise, create a modular analytics persistence layer compatible with the existing architecture.

If PostgreSQL is available, design appropriate tables and indexes for analytics events, daily aggregates, and financial summaries.

Keep raw events and aggregated reporting data logically separate.

Apply strict authorization so users can access only their own private analytics and authorized financial records.

Do not expose administrative analytics endpoints to ordinary users.

Use server-side validation for sensitive events and financial calculations.

Avoid unbounded raw event storage. Establish a reasonable retention and aggregation strategy.

Do not introduce a new managed database or paid analytics vendor without documenting why it is needed.

10. PERFORMANCE AND FUTURE COMPATIBILITY

Build analytics services and event schemas so they can be reused by a future native mobile application.

Keep tracking independent of specific browser APIs wherever practical.

Make charts and metric cards reusable components.

Use pagination and date-range queries instead of loading an entire account’s event history.

Avoid expensive queries on every dashboard request. Use suitable aggregation and caching strategies.

Ensure that unavailable browser tracking, blocked scripts, or delayed network requests do not crash the application.

11. IMPLEMENTATION AND QUALITY ASSURANCE

First inspect the current application and identify existing data sources, content types, authentication, backend routes, and monetization models.

Then implement the feature in stages:

Stage 1: Dashboard interface and navigation.

Stage 2: Real profile visit, content view, engagement, and follower analytics.

Stage 3: Content-specific analytics and audience reporting.

Stage 4: Growth insights.

Stage 5: Earnings integration with existing verified transaction records.

Test authorization, date filters, aggregation accuracy, duplicate event handling, mobile responsiveness, empty states, and failure recovery.

Verify that analytics never leak private user data.

Do not mark a feature complete merely because its screen renders.

At completion, provide a report describing:

* Files changed.
* Database changes.
* New event types.
* Metrics implemented and their precise definitions.
* Metrics still unavailable.
* Any environment variables required.
* Any external services or additional costs.
* Tests performed and their results.

Build a functioning analytics system, not a static demo. Preserve all existing Oldtimehive functionality.
